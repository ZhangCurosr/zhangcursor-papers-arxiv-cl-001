# 论文速读：CROCODIL—Cross-Model Code Editing with LLMs

## 一句话总结
本文发现 LLM 在编辑由其他 LLM 生成的"外国代码"时会进行更多、更过度的修改；为此提出 CROCODIL，一种基于 GRPO 的后训练框架，通过组合"相似性奖励"（惩罚大幅改动）与"执行奖励"（奖励编译与测试通过），在保持功能正确性的同时显著压缩跨模型代码编辑的修改量。

## 研究问题与动机
- **多模型协作现实**：开发团队经常同时使用多个 LLM 助手，不同开发者偏好不同模型，同一开发者也可能在不同会话中切换模型，导致某模型被要求编辑的"预编辑代码"往往并非出自自身风格。
- **风格差异引发过度编辑**：不同模型训练语料与后训练目标不同，形成各自风格偏好；本文首次系统提出并验证：LLM 在编辑"外国代码"时会比编辑"自生代码"做出更多、有时是过度的变更。
- **现有基准不足**：既有代码编辑基准（如 Can It Edit、EDIT-Bench、SWE-agent）只允许改变编辑器模型，无法独立控制"预编辑代码的作者"，因而无法回答"编辑器行为在多大程度上由原作者风格驱动"这一因果问题。
- **工程收益诉求**：每次 PR 的改动量越小，代码审查越快、需要重跑的单测越少、整体研发节奏越顺畅；减少"与任务无关的过度编辑"具有明确工业价值。

## 核心贡献（创新点）
1. **首次量化"跨模型过度编辑"现象**：在 5 个 LLM、16 对（实现者×编辑器）组合上，4 个开源模型在 14/16 对上都显著更少地修改自己实现的代码；这一差距无法通过 prompt engineering 关闭。
2. **提出 CROCODIL 奖励设计**：将"相似性奖励"（以开发者原始 PR 改动量为参考尺度、惩罚模型改动过大）与"执行奖励"（编译成功 + 旧测试通过率 + 新测试通过率加权）相乘，鼓励策略在不动功能的前提下尽量小改。
3. **构建可分离作者/编辑器的 Rust PR 语料管道**：从 crates.io 的合并 PR 中按函数粒度切分，配合线覆盖率采集器筛选出能分别校验"预编辑版"与"后编辑版"行为的测试集，支撑后续可复现评测。
4. **实证证明 RL 训练优于提示工程**：对比"严格提示（Strict）"与"RL 微调（RL）"，前者仅在部分实现者上小幅降低改动量，且在 Haiku/Olmo3 自编辑上反而增大；后者在保留通过率的子集上始终更小。

## 方法详解
- **任务形式化**：将函数编辑视为序列级强化学习问题——给定已实现的预编辑函数 $f^A_{\text{pre-edit}}$、任务描述 $d$ 与上下文 $\mathcal{C}$，策略 $\pi_\theta$ 输出编辑后函数 $f^A_{\text{post-edit}}=\pi_\theta(f^A_{\text{pre-edit}}, d, \mathcal{C})$；每次 rollout 获得标量奖励 $R_{\text{CROCODIL}}=R_{\text{sim}}\times R_{\text{exec}}$，并用 GRPO 优化 $\pi_\theta$。
- **相似性奖励**：令 $D_m=(c_m+1)(l_m+1)$ 为模型改动字符数与行数的乘积，$D_h=(c_h+1)(l_h+1)$ 为开发者原 PR 的同等乘积（视为"任务量"估计）；取 $R_{\text{sim}}=\frac{1}{1+\alpha\cdot D_m/D_h}$，其中 $\alpha=0.33$，使与开发者改动同量的编辑得分约为 $\frac{1}{1+\alpha}\approx0.75$，更大改动被单调压制。
- **执行奖励**：$R_{\text{exec}}=w_b\cdot b+w_{\text{pre}}\cdot p_{\text{pre}}+w_{\text{post}}\cdot p_{\text{post}}$，$b$ 为编译是否通过，$p_{\text{pre}}$ 为对"实现已通过的旧测试"的通过率（防回归），$p_{\text{post}}$ 为对"实现未通过的后编辑测试"的通过率（引入新行为）；训练时设 $w_b=0.2,w_{\text{pre}}=0.4,w_{\text{post}}=0.4$。
- **训练设置**：以 Olmo3 7B 为底座（因其在评测中最激进），用 LoRA（rank=32、alpha=64）冻结基座权重，VERL 框架实现 GRPO；3 轮、batch=32、每提示 8 次 rollout、温度 1.0、学习率 $3\times10^{-5}$、KL 正则系数 0.001；训练集 355 个跨编辑任务、验证集 39 个，与评测仓库零重叠。

## 实验与结果
- **数据集**：从 crates.io 收集 4,514 个 Rust PR、8,235 个函数（过滤后留 2,442 个可实施函数）；测试覆盖平均 87.9%、中位数 94.5% 的开发者后编辑代码行。
- **基线**：（1）Olmo3 7B Base（未训练）；（2）Olmo3 7B Strict（相同任务提示外加"最小化改动"系统指南）；（3）Olmo3 7B RL（CROCODIL）。
- **主要定量结论**（全部任务列，Table 4）：CROCODIL 将 Olmo3 7B 在所有 4 个开源实现者上的归一化 Levenshtein 字符级编辑距离**几乎减半**（如 Qwen3.5 0.54→0.20、GPT-OSS 0.54→0.22、Olmo3.1 0.51→0.24、Haiku 0.45→0.15）；在同一实现者下对 Olmo3 7B 自身的自编辑仅微降（0.47→0.21，符合预期）。
- **通过后子集仍更小**（Base & RL pass）：在两者均通过测试的任务交集上，RL 模型在 Qwen3.5/GPT-OSS/Olmo3.1/Haiku 四家实现者上依然更小，仅在对 Olmo3 实现者上劣于 Base（4 个任务、†标注）。
- **严格提示不稳定**：All tasks 列仅在 Qwen3.5/GPT-OSS/Olmo3.1 上小幅下降，且在 Olmo3/Haiku 上反而上升；Base & Strict pass 列仅在 Olmo3.1 上优于 Base——证明单纯提示无法一致地压降改动量。
- **成功率提升**（Table 5）：除 Olmo3 自编辑外，RL 在所有实现者上的 Build / All Tests / Mean Tests 三项指标均超过 Base 与 Strict；严格提示在 Olmo3 自编辑的 All Tests 上明显低于 Base（12.66% vs 24.05%）。
- **排除"不做任何改动"的作弊**：RL 有 19.94% 输出为无变更响应；剔除该类后、仅统计"确实修改"的任务（Table 6），RL 在除 Olmo3 以外的所有实现者上 Build 率仍更高（如 Haiku 实现者 42.86% vs 33.15%）。
- **定性案例**（Figure 5/6）：成功时，Base 常超范围地加入虚构 enum 或 helper；RL 严格限定在 match 块内新增所需 arm。失败时，RL 因相似度惩罚在"标识符重命名传播"类小任务上更易拒绝完成改动。

## 相关工作脉络
- **代码编辑/修复基准**：CoditT5（显式建模编辑的预训练目标）、Can It Edit/EditPackFT（Python commit 清洗）、EDIT-Bench（VS Code 插件真实指令+人工写测试）、SWE-agent（ACI 工具链）、Agentless（三阶段定位-修复-验证、无需工具决策）——本文不在"提升编辑求解能力"上竞争，而在"让编辑更小、更少过度改动"上提供正交视角。
- **代码 RL 奖励设计**：CodeRL（编译器密集反馈）、RLTF（单元级失败定位）、StepCoder（课程子任务+屏蔽未执行代码）——这些以"输出正确性"为核心；CROCODIL 在此基础上额外引入与"开发者原始改动量"对齐的相似性奖励，使奖励空间从仅关注 correctness 扩展到兼顾 conciseness。
- **长度膨胀治理**：GR3（Li et al., 2026）以组内均值归一化长度并惩罚长回复；本文借鉴其归一化思路但把参照系换成"开发者 PR 的任务量 $D_h$"，从而直接把"跨模型风格漂移引发的过度编辑"纳入优化目标。
- **跨模型/跨作者研究空白**：既有工作基本把 pre-edit code 视为中立输入，不区分"谁写的"；本文通过可分离作者/编辑器的数据管道首次给出可统计检验的证据（MWU 单侧检验，14/16 对显著）。

## 局限性与未来方向
- **单一语言局限**：语料与训练数据全部来自 Rust crates；对 Python/JavaScript 等弱类型或语法差异更大的语言，跨编辑模式与 CROCODIL 有效性均未验证。
- **函数级作用域**：为控制上下文规模，将 PR 拆成 20–200 非空行的单函数编辑任务；多函数或多文件级联变更不在此范围内。
- **模型池有限**：仅 5 个 LLM（4 开源 + Haiku 4.5），且只对 Olmo3 7B 做 CROCODIL 训练；GPT-5、Claude Opus 等大闭源模型未被评测，也未对它们训练。
- **Haiku 反例未解释**：Haiku 4.5 未呈现"自编辑<跨编辑"的规律，其列最小值落在 GPT-OSS 实现上，机制不明——作者认为值得作为有趣未来方向。
- **过度保守的副作用**：相似度惩罚使 RL 模型约 20% 输出为"无变更"，且在需传播重命名的微小任务上更容易拒绝执行，导致部分本可由 Base 成功完成的任务 RL 失败。

## 研究启发与可借鉴点
- **可迁移的奖励构造范式**：将"与参考人类改动量的比例"作为正则化奖励，并乘以执行成功率，这种"尺寸感知 × 正确性"的复合奖励可迁移至任何需要同时优化"质量"与"节俭"的代码生成/编辑任务（如 refactoring、format-preserving transformation）。
- **可复用的数据管道设计**：以 GitHub PR 的 base/head/max 三提交组合 + 行覆盖率采集器筛出精准定位预/后编辑行为的测试集，这种"开发者意图可检验"的数据构造方法可直接用于训练代码补丁、最小化重构等任务。
- **实验设计亮点**：同时枚举"实现者×编辑器"两维度、在同一任务上做 min-max 归一化后再做 MWU 单侧检验，既能控制任务难度差异又能给出统计显著性，适合任何"风格/作者效应"类研究。
- **与团队方向的结合机会**：（1）把 CROCODIL 的相似度奖励嫁接至团队现有的代码审查摘要生成、diff 压缩、或 changelog 抽取任务上，迫使模型输出更贴近人工 reviewer 的预期粒度；（2）在多模型协作的 IDE 插件中，动态加载/卸载 LoRA adapter 以区分"自编辑"与"跨编辑"场景（论文已暗示该用法可行）。

## 关键术语表
- **跨编辑（cross-edit）**：编辑器 LLM 对由另一 LLM 实现的外国代码应用 PR 变更的任务设定，区别于"自编辑"（self-edit）。
- **相似性奖励（similarity reward）**：以模型改动量与开发者原始 PR 改动量的比值为惩罚核心、形如 $\frac{1}{1+\alpha D_m/D_h}$ 的平滑递减奖励。
- **执行奖励（execution reward）**：由编译成功与两类测试通过率（旧测试防回归、新测试引新行为）线性加权构成的 correctness 奖励。
- **GRPO（Group Relative Policy Optimization）**：DeepSeekMath 提出的近端策略优化变体，在本工作里用于优化 CROCODIL 的复合奖励。
- **Levenshtein 字符级编辑距离**：本文衡量"编辑幅度"的主指标，经 rustfmt 格式化、去注释空白后计算，并在任务内做 min-max 归一化。
- **Mann-Whitney U（MWU）单侧检验**：用于检验"自编辑距离是否系统小于跨编辑距离"的统计显著性测试。
- **严格提示（strict prompt）**：在系统提示中加入"只做任务必要改动、保留控制流/类型/变量名/错误处理风格"等 guidelines 的 prompt engineering 对照基线。
- **LoRA adapter 按需加载**：因 LoRA 冻结基座权重，推理时可按需加载以切换至 CROCODIL 行为，对自编辑场景可回退到基座。

## 可复现要素
- **代码**：论文已开源，仓库 https://github.com/EngineeringSoftware/Crocodil。
- **数据集**：训练集 355 个跨编辑任务（150 仓库）、验证集 39 个；评测集来自 356 个仓库的 2,458 个可采测试函数（最终每实现者 79–603 不等）；论文未声明数据公开链接，需按文中过滤条件自行重建。
- **关键超参**：LoRA rank=32、alpha=64；GRPO batch=32、rollouts/prompt=8、温度=1.0、epoch=3、lr=$3\times10^{-5}$、KL 系数=0.001；相似度奖励 $\alpha=0.33$；执行奖励 $w_b=0.2,w_{\text{pre}}=0.4,w_{\text{post}}=0.4$；10,000-token 上下文窗口（训练时为 12,288 总 token、6,144 输出预留）。
- **模型**：开源底座 Olmo3 7B（Thinking）、Qwen3.5 35B A3B、GPT-OSS 20B、Olmo3.1 32B；闭源 Haiku 4.5。
- **工具**：VERL 框架训练；Python difflib（gestalt-pattern-matching）做重叠过滤；Rust 行覆盖率采集器筛选测试。
