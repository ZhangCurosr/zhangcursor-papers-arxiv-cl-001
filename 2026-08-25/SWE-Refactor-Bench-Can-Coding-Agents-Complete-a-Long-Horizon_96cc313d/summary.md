# 论文速读：SWE-Refactor-Bench: Can Coding Agents Complete a Long-Horizon, Whole-Repository Stack Migration?

## 一句话总结
本文提出 **SWE Refactor Bench**，一个包含 20 个真实开源项目全仓库迁移任务（覆盖语言/框架/平台/构建工具链四类技术债）的基准测试，设计三阶段评估协议同时检验迁移完整性和行为正确性；实验表明当前最强 AI 编程智能体仅 5.4%（28/520）的尝试能通过全部三阶段，说明全自动全仓库迁移仍远未可靠。

## 研究问题与动机
- **核心问题**：AI 编程智能体能否自主完成长周期、全仓库级别的技术栈迁移，并保证行为正确？
- **盲区（Blindness）问题**：现有基准仅用固定行为测试集评估迁移质量，而原始仓库的行为测试通过率已达 100%，因此"什么都不做"的仓库同样能通过所有测试——固定测试无法区分"已完成迁移"和"未做任何迁移"，导致评估失效。
- **迁移完整性和行为正确性是两种不同能力**：前者要求目标栈真正替换旧实现，后者要求可观测行为完全保持一致；单一评估维度均会导致误判（无迁移则全对，有迁移则可能破坏行为）。
- **已有基准的定位不足**：SWE-bench 等以"红→绿"转变（测试从失败到通过）为信号，但全仓库迁移的起点已经是全绿状态，该信号不存在；现有代码迁移基准（如 MigrationBench）仅改变语言版本或单 API，不涉及全栈替换。

## 核心贡献（创新点）
- **定义并揭示盲区（Blindness）现象**：首次明确指出行为-only 评估存在系统性缺陷——不迁移的仓库可获得满分行为测试分数，这是评估指标本身的结构性盲点而非模型能力不足。
- **提出 SWE Refactor Bench 基准**：包含来自真实基础设施（SQLite、zlib、libsodium 等 20 个上游项目）的 20 个全仓库迁移任务，覆盖语言（7）、框架（7）、平台（3）、构建工具链（3）四类技术债，总代码量 867,062 LoC。
- **设计三阶段对抗性评估协议**：第一阶段 Migration Audit 验证迁移是否真实发生（硬性否决门），第二阶段 Behavioural Tests 使用 130,118 个预录制行为检查，第三阶段 Agentic Verification 派遣 6 个独立编程智能体逐一小时搜索隐藏行为差异——三个阶段分别对应"迁移是否发生"、"已知行为是否保留"、"未知差异是否存在"三个独立证据。
- **揭示当前智能体的能力缺口**：最强模型 claude-opus-5 得分 47.0/100，88 个通过前两阶段的提交中 60 个（68.2%）被第三阶段验证器推翻；迁移完整性与行为正确性呈反向失败模式（30 个跳过迁移但通过行为测试 vs 252 个完成迁移但破坏行为）。

## 方法详解
- **任务形式化**：迁移任务定义为 tuple $\tau = (R_A, \Sigma_A \to \Sigma_B, \mathcal{O}, \mathcal{T}, E, B)$，其中 $R_A$ 是 State A（可构建运行的原始仓库），$\Sigma_A \to \Sigma_B$ 是目标栈替换（语言/框架/平台/构建工具链之一），$\mathcal{O}$ 是可观测接口，$\mathcal{T}$ 是给智能体的指令，$E$ 是离线容器镜像，$B$ 是时间预算（6–30 小时）。
- **两个必要条件**：迁移条件（$\Sigma_B$ 构建交付产物且 $\Sigma_A$ 从仓库和构建闭包中消失）与保留条件（$\mathcal{O}(R_S) = \mathcal{O}(R_A)$，行为完全一致）。
- **三阶段协议**：
  - **Stage I – Migration Audit**：针对每个仓库编写 prompt 形式的验证问题（如"是否仍有 C 源码残留""Rust 是否为实际实现"而非仅包裹 shim），每个标准由模型独立评判 3 次取多数票，任一标准失败即一票否决。
  - **Stage II – Behavioural Tests**：基于 State A 的参考构建和运行录制 130,118 个固定检查（136 个模块），每个输入必须产生与原始完全相同的输出和退出状态；Stage II 是"全或无"——只要有一个检查失败即得 0 分。
  - **Stage III – Agentic Verification**：6 个独立编程智能体（其中 5 个各负责一个指定方向，1 个无限制），每个持有原始和迁移后两份代码库，限时 1 小时生成差异化测试用例；必须提交可执行的 counterexample（在原始通过但在迁移结果失败），且需先通过原始代码的绿色验证再复现 3 次以上以排除 flaky 测试。
- **评分公式**：$S(\tau) = \mathbf{1}[g = \text{pass}] \cdot \mathbf{1}[r_i = 1\ \forall i] \cdot \left(0.4 + 0.6 \cdot \frac{s}{6}\right)$，其中 $g$ 为 Stage I 判决，$r_i$ 为 Stage II 各模块通过率，$s$ 为未能找到反例的验证器数量；Stage I 是乘法因子（无迁移则零分），Stage III 占 0.6 权重（最大不确定性部分给予更大分量）。
- **隔离设计**：所有评估标准（Stage I–III）存在于智能体容器之外，智能体完全无法"看到"测试内容，防止过拟合或针对性绕过。

## 实验与结果
- **数据集**：20 个真实开源项目的全仓库迁移任务，涵盖 4 类技术债，共 867,062 LoC，130,118 个行为检查。
- **评估模型**：8 个前沿模型（claude-opus-5、gpt-5.6-sol/luna、kimi-k3、qwen3.8-max、deepseek-v4-flash、glm-5.2），26 个模型-努力配置。
- **关键数字**：
  - 520 次运行中仅 **28 次（5.4%）通过全部三阶段**，13 个任务无任何模型获得可接受解。
  - 最强模型 **claude-opus-5 得分 47.0/100**（5 次接受），其次为 gpt-5.6-sol（28.5）、kimi-k3（19.5）、claude-sonnet-5（15.0）。
  - 340 个通过 Stage I 的提交中，58% 达到 99% 固定检查，但仅 **26% 达到 100%**。
  - 88 个 Stage II 完美的提交中，60 个（**68.2%**）被 Stage III 验证器推翻。
- **按类别分解**：构建工具链迁移表现最好（得分 31.4），语言迁移最差（得分 5.6）；框架迁移贡献了 14/28 次接受的半数。
- **盲区现象直接验证**：gpt-5.6-luna、deepseek-v4-flash、glm-5.2 三个模型各有多次运行通过所有固定检查但从未完成实际迁移（4、3、3 次），若仅看行为测试会误报为"完美解决"。

## 相关工作脉络
- **SWE-bench 范式**：以"红→绿"转变作为任务完成证据，适用于 bug 修复但无法用于行为保持型迁移（起点已为全绿），本文与之一脉相承但解决了该范式在迁移场景下的失效问题。
- **TransCoder / 代码翻译基准**：早期工作聚焦函数级语言翻译，本文扩展到全仓库级跨栈迁移（含框架、平台、构建工具链），突破了纯代码翻译的范畴。
- **MigrationBench**：仅迁移语言版本（Java 8 → 17/21），语言本身不变；本文涉及真正的技术栈替换（如 C → Rust、POSIX → WASI）。
- **差分测试（Differential Testing）**：Stage III 借鉴编译器验证中的差分测试思想，但将其扩展为 agentic 形式——由独立编程智能体主动搜索差异而非静态分析，适合跨语言全仓库场景。
- **模型作为裁判（LLM-as-a-Judge）**：Stage I 采用模型评判，但通过多样本投票、证据引用和与人类标注对比（κ=0.795）来缓解偏见，相较一般 LLM 评判工作更具工程严谨性。
- **奖励黑客（Reward Hacking）文献**：本文发现的行为盲区不是模型 exploiting 漏洞，而是评估规则本身无法观测迁移是否发生，这与 SWE-bench 的污染问题性质不同。

## 局限性与未来方向
- **任务数量有限**：20 个任务对于建立统计显著的结论仍然偏少，且覆盖的技术栈类别有限。
- **Stage I 依赖模型评判**：虽然经多轮投票和人类对照验证了较高一致性，但模型裁判仍存在位置偏差、冗长偏好等已知问题，可能引入系统性误差（实证表明裁判倾向于更严格而非更宽松）。
- **Stage III 验证器强度直接影响分数**：最强的 claude-opus-5 持有 2 个验证器席位且 break rate 远高于其他（55.7% vs 21.6%–26.1%），这意味着分数反映的是特定验证器面板的特性，而非绝对正确性。
- **未来方向**：随着底层模型能力提升，同一基准的验证将更加严格；需要探索如何将差分测试的形式化思想（translation validation、差分符号执行）应用于跨语言全仓库场景。

## 研究启发与可借鉴点
- **"Blindness"诊断思路可迁移**：在设计任何以行为测试为唯一指标的评估协议时，应主动考虑"不做任何修改即可得满分"的可能性，这是评测设计的一般性反套路检查项。
- **三阶段正交证据设计值得复用**：将"结构完整性检验"、"行为正确性检验"和"对抗性差分搜索"三层证据串联，每层测量不同维度的属性且互不可替代，为复杂任务的评估提供了结构化模板。
- **Agentic Verification 的对抗性差分测试方法**：让多个独立智能体分别搜索不同方向的差异，并以"可执行 counterexample"而非"文本报告"作为否决依据，兼顾了可验证性和可操作性，可作为自动化验证的新范式。
- **与团队方向结合机会**：若团队涉及代码迁移、自动重构或软件工程自动化，此基准可作为评估系统级迁移能力的严格测试床；三阶段协议可直接嵌入内部 CI/CD 流程作为迁移质量的验收标准。
- **Stage I 裁判机制的工程化设计**：多轮独立评判 + 证据引用 + 多数投票 + 与人类标注对照的四重保障，为 LLM 作为裁判的具体实现提供了高质量参考。

## 关键术语表
- **Blindness（盲区）**：行为-only 评估的系统性缺陷，指"未做任何迁移的仓库"因原始行为测试本就已经通过，而获得满分的不合理现象。
- **Migration Audit（迁移审计）**：三阶段评估的第一阶段，通过模型驱动的 prompt 问答验证目标栈是否真正替换了旧实现，任一标准失败即一票否决。
- **Agentic Verification（智能体验证）**：三阶段评估的第三阶段，派遣 6 个独立编程智能体在原始与迁移后的代码库之间搜索隐藏的行为差异，仅接受可执行的反例。
- **技术债迁移（Technical Debt Migration）**：将整个仓库从一套技术栈（语言/框架/平台/构建工具链）迁移到另一套，要求可观测行为完全保持不变。
- **Differential Testing（差分测试）**：将同一输入同时作用于两个实现并比较输出差异以检测错误的测试方法，此处扩展为 agentic 形式。
- **Load-bearing Stack（承载性技术栈）**：指仓库的核心设计依赖于该技术栈（而非仅是 import 语句），移除它会触及根本架构设计。

- **代码/权重**：论文声明了项目主页但未明确说明是否开源代码；模型 API 调用依赖 claude-opus-5、gpt-5.6-sol/luna 等商业模型
