## ABSTRACT

The increasing use of large language models for code generation has created an urgent need for reliable methods to distinguish purely human-written code from AI-involved code — files in which any part was generated or substantially modified by a model, however small that part is. Our goal is not only to determine whether a program is purely human-written or has been generated or modified by AI, but also to localize the specific lines or blocks attributable to AI. Existing approaches typically compress a file into a single score, either from surface-level stylistic features or from a global code representation, which averages away the evidence when only a few blocks of a file are AI-involved. We propose a detection framework that models AI authorship at the token level and supports predictions at the line, block, and file levels. A frozen code language model is equipped with two low-rank adapters, trained separately on machine-written and human-written files. The per-token log-likelihood ratio between the two adapters provides local evidence of AI authorship. Lightweight prediction heads then aggregate this evidence within lines and blocks, using the surrounding code context to estimate the probability that each line or block was generated or substantially modified by AI. The resulting local predictions are further aggregated to produce a file-level decision. We train these predictions using mixed-authorship files constructed from human originals and their AI-generated or AI-modified counterparts, including continuation and fill-in-the-middle scenarios. On an internal test set of 11,773 AIinvolved files across six generation regimes against a shared pool of 2,541 human files, our method reaches 72.4 macro F1 at a 1% FPR operating point. With no adaptation at all, the method reaches 62.5 line-level F1 on HybridCodeAuthorship (Patterson et al., 2026), an external human–AI co-writing benchmark that ships no training split, above the 56 that the benchmark’s own paper reports as its best line-level result. We further run an extra transfer evaluation on a humanwritten-only test set: across 19,445 files from repositories created before 2022, our false-positive rate stays between 0.55 and 0.81% when the false-positive rate threshold is transported at 1%. So the operating point remains valid after transferring from paired synthetic negatives to real human code.

## 1 INTRODUCTION

Assistants that write code inside an existing file have moved the unit of authorship below the file. A commit may contain a completed function body, a refilled interior span, or a locally refactored block, with the rest of the file untouched. The question a provenance tool has to answer is therefore not only was this file written by a model but is any part of it, and, if a reviewer is to act on the answer, which part.

Two families of detectors dominate the current literature, and both answer only the first question. Zero-shot likelihood statistics score a file against a reference language model and threshold a scalar summary: log-rank (Gehrmann et al., 2019), LRR (Su et al., 2023), perturbation curvature (Mitchell et al., 2023; Bao et al., 2024), or cross-perplexity between two models (Hans et al., 2024). Supervised detectors fine-tune a code encoder (Feng et al., 2020; Guo et al., 2022; Wang et al., 2023a) or align a proxy model to machine style (Chen et al., 2025) and read a single decision out of a global representation. In both cases the file is compressed to one number before any decision is made, which is adequate when the whole file is machine written and lossy when only a few blocks are.

Mixed authorship breaks these detectors in two distinct ways. A global score averages a short AI span together with the human majority of the file, so the evidence is diluted in proportion to the AI fraction. Independently, the span itself is weaker evidence than a whole machine-written file, because the model that produced it was conditioned on the surrounding human code and inherited its naming and layout. Our measurements show both effects: on the two interior-segment test cells, the strongest supervised file-level baseline drops to 0.647 and 0.565 AUROC, while the same detector reaches 0.945–0.963 on the from-scratch cells.

We therefore keep the evidence local for as long as possible. A single frozen code language model is equipped with two LoRA adapters (Hu et al., 2022), trained with a plain causal language modeling objective on machine-written and on human-written files respectively; neither has a classification head. Their per-token log-likelihood ratio is a local score whose human-side term cancels the confound of how predictable a token is in the first place.

Evaluating this design requires separating what a detector cannot represent from what its training distribution never contained. The transfer–adaptation gap on external benchmarks is the sharpest finding in the paper, and we read it as a statement about training corpora rather than detector capacity.

The main contributions of this paper are:

• A detection framework that couples a token-level likelihood ratio with line- and blocklevel supervised heads over a single frozen code language model, so that local generation evidence and its surrounding context are modeled jointly rather than as alternatives.

• A mixed-authorship data construction protocol that synthesizes continuation and fill-in-themiddle edits with character-level ground truth and a controlled AI ratio $\rho ,$ which supplies within-file supervision for the line and block heads and test cells covering both tail and interior segment geometries. Appendix A.5 ablates the training-side composition and finds corpus volume, rather than the mixture of forms, to be the load-bearing factor.

• An evaluation protocol that separates capacity from distribution on external benchmarks under two protocols (zero-adaptation transfer and per-benchmark adaptation), reporting results at the file, block and line granularities, together with a carrier-artifact control and a false-positive measurement on real repository code.

We defer a full discussion of related work to Appendix A.1.

## 2 PROBLEM FORMULATION

Let $\boldsymbol { x } = ( x _ { 1 } , \dots , x _ { T } )$ be the token sequence of a source file. The file-level label is binary and AI-involved: $y = 1$ if any part of the file was generated by a language model, and $y = 0$ if the file is entirely human-written. Mixed files therefore carry y = 1 regardless of how little of the file is machine-written, which is the convention used in machine-revised-text detection (Chen et al., 2025) and by the machine-refined class of DroidCollection (Orel et al., 2025). A detector scores the file and thresholds that score at $\tau ,$ , calibrated on human files at a target false-positive rate. The detector sees the file alone at test time: no repository metadata, commit history or generation-side information is available.

Ground truth for a mixed file is a set of character intervals covering its machine-written text. A line is an AI line if any of its characters falls inside one of those intervals. The AI ratio $\rho$ is the fraction of AI lines in the file, over all lines including blank ones; our synthesized mixed files carry $\rho \ge 0 . 0 5$ by construction (Section 3.4) and pure AI files have $\rho = 1$ . A block is a run of K consecutive lines with $K \in \{ 8 , 1 6 \}$ , cut from the first line of the file; the last block keeps whatever fewer than K lines remain, since dropping it would exclude the end of the file from prediction and the machine-written tail of continuation files sits exactly there. Block b carries the label $z _ { b } = 1$ if it contains at least one AI line and $z _ { b } = 0$ otherwise, so a block whose AI lines cover only part of it is positive while being mixed in content. Blocks and lines are the two prediction units we report. Every line-level number in the paper is computed against these line labels, and every block-level number against these block labels except where a caption states the convention it departs to.

## 3 METHOD

## 3.1 TOKEN-LEVEL LIKELIHOOD RATIO

We keep a single code language model $p _ { \theta }$ frozen and train two low-rank adapters (Hu et al., 2022) on it with a plain causal language modeling objective: an AI-side adapter on machine-written files and a human-side adapter on human-written files. Neither adapter has a classification head. The per-token score is the log-likelihood ratio

$$
s _ { t } \ = \ \log p _ { \mathrm { a i } } ( x _ { t } \mid x _ { < t } ) \ - \ \log p _ { \mathrm { h u m } } ( x _ { t } \mid x _ { < t } ) ,\tag{1}
$$

which we decompose through the frozen base model as $s _ { \mathrm { a i - h u m } } ~ = ~ s _ { \mathrm { a i - b a s e } } + s _ { \mathrm { b a s e - h u m } } ,$ , where $s _ { \mathrm { a i - b a s e } } = \log p _ { \mathrm { a i } } - \log p _ { \theta }$ and $s _ { \mathrm { b a s e - h u m } } = \log p _ { \theta } - \log p _ { \mathrm { h u m } }$ are the two adapters’ deviations from the shared base model. Neither half is sufficient on its own: subtracting the human-side term cancels the confound of how predictable the text is in the first place, which a single-sided score cannot separate from authorship (Section 5.3).

Both adapters are rank-16 LoRA modules with α = 32 (18.5M trainable parameters per side, 36.9M in total), trained for one epoch in fp16 on the pure-file split, with no packing and token-budget batching. The frozen backbone is Qwen2.5-Coder-1.5B (Hui et al., 2024).

## 3.2 LINE- AND BLOCK-LEVEL DISCRIMINATIVE HEADS

Token scores are mapped to lines (a token belongs to the line containing its last character) and then to fixed-K blocks. Each block is described by 88 features in five families: raw statistics of $s _ { t } .$ , of the base-model profile (negative log-likelihood, entropy, rank) and of dctx, the gap between the long- and short-context negative log-likelihood of the same token under each of the three passes; within-file z-scores of those statistics; neighbouring-block contrasts; positional features; and language identity (Table 21). A sequence head (bidirectional GRU; Cho et al., 2014) reads the block sequence of a file and emits a per-block AI probability $\hat { z } _ { b } .$ . The head is trained only on blocks that are entirely AI or entirely human, while reading the whole file, mixed blocks included, as context; at inference it scores every block, and block-level metrics are computed against $z _ { b }$ over all blocks.

The line head is the same construction one granularity finer: a bidirectional GRU over the per-token signal sequence, mean-pooled to one logit and one AI probability $\hat { z } _ { \ell }$ per line. Line labels come directly from the AI intervals, so no line has to be held out of the loss. Both heads consume the same token-level profile, each signal paired with its within-file z-score, and differ in where it is pooled, the block head into per-block statistics before the sequence model and the line head only after it, as well as in their feature sets (Appendix A.8). Which granularity is preferable depend on the regime, so we report both: Section 5.2 gives their behaviour against AI segment length; a syntax-aligned alternative to the fixed grid and the two heads at equal input are in Appendix A.5.

## 3.3 AGGREGATION TO A FILE-LEVEL SCORE

Each read-out produces a file-level score $f ( x )$ by averaging its own units: the token ratio over the T tokens of the file, the block head over the logits of the block set B, and the line head over the logits of the L lines,

$$
f _ { \mathrm { l r } } ( \boldsymbol { x } ) = \frac { 1 } { T } \sum _ { t = 1 } ^ { T } s _ { t } , \quad f _ { \mathrm { b l k } } ( \boldsymbol { x } ) = \frac { 1 } { | \mathcal { B } | } \sum _ { b \in \mathcal { B } } \sigma ^ { - 1 } ( \hat { \boldsymbol { z } } _ { b } ) , \quad f _ { \mathrm { l i n } } ( \boldsymbol { x } ) = \frac { 1 } { L } \sum _ { \ell = 1 } ^ { L } \sigma ^ { - 1 } ( \hat { \boldsymbol { z } } _ { \ell } ) ,\tag{2}
$$

where $\sigma ^ { - 1 }$ is the logit function. The mean is the selected form in all three cases and not the only one we tried: for the token score we compare it against a sliding-window maximum, a change-point tail mean and the best segment after binary segmentation (Truong et al., 2020; Killick et al., 2012), and for each head against a per-unit maximum and a learned attention aggregator over unit states. The aggregator and the block size K are selected on the development split and applied to test unchanged.

Thresholds are calibrated as stated in Section 4.4, except where a table states otherwise: the block and line read-outs use thresholds frozen on the development split and transported unchanged, both at their own granularity and, in Section 5.5, to the pre-2022 repository corpus, which is disjoint from the internal paired HUMAN cell.

## 3.4 CONSTRUCTING MIXED-AUTHORSHIP SUPERVISION

Supervision at either granularity requires files whose authorship is heterogeneous and known. We synthesize two forms. In continuation a model completes a file from its first N% of lines, which gives exactly one AI segment at the tail. In fill-in-the-middle one or more spans are removed and refilled, which gives interior segments (Bavarian et al., 2022); the number of holes is sampled from {1, 2, 3, 5, 8}. Sampling is constrained so that ρ is balanced over five buckets covering [0.05, 1.0], with the cut point or the hole coverage solved backwards from the target ρ and resampled when the realized ratio falls outside its bucket. AI spans are recorded as exact whole-line character intervals. For every mixed file we additionally keep its original human version as a negative example, so the heads see "no boundary anywhere" files that are otherwise textually paired with positives.

Two properties of this construction bound what the heads can learn. Both forms produce long segments — the median AI segment in the training and development splits is 20 non-blank lines — so the scattered short-segment regime that in-place refactoring produces is absent from training and appears only on the test side, where we read it as out-of-distribution measurement rather than as a held-out sample of the training regime. The dual-LoRA backbone, by contrast, is trained on pure files only. The development split used for aggregation and threshold selection does contain mixed files, because the score of a file moves with its AI ratio ρ: pure files sit at the extremes, one mode per class, while a partially machine-written file falls between them. A development split of pure file alone would fix the aggregator choice at scores the mixed part of the test set almost never produces.

## 4 EXPERIMENTAL SETUP

## 4.1 INTERNAL DATASET

Files are drawn from public repositories and paired with machine-written counterparts produced by a two-stage protocol in which a reader model summarizes a file into a specification and a writer model reimplements the file from the specification alone, without seeing the original. The isolation is deliberate: a writer that sees the original produces a rewrite, and a detector trained on rewrites learns rewriting artifacts. The reader is GPT-5.6 decoded at temperature 0; the writers are Claude Opus 5, DeepSeek-V4-Flash, GPT-5.6 and GLM-5.2, all decoded at temperature 0.7, and every file is assigned to one of them at random so that each contributes about a quarter of the machine-written side. Mixing writers dilutes single-model length and comment-density fingerprints. Splits are cut by repository hash, so no repository appears on both sides of a split.

Table 20 (Appendix A.8) summarizes the splits: the two LoRA adapters train on 12,002 pure human/AI files, the block head on 1,582 mixed files (843 continuation and 739 fill-in-the-middle) together with their 1,582 human originals, and the aggregator, K and decision thresholds are fixed on 4,062 pure and 398 mixed development files. The test set applies one generation axis at a time to a fixed human base — 11,773 positives over six generation cells against a shared pool of 2,541 human negatives.

## 4.2 TEST CELLS

The test set varies one axis at a time over a fixed human base: HUMAN (the only negative cell), BASELINE (specification-based rewriting with the training writer models), UNSEEN-MODELS (same protocol with four writer models never seen in training: Qwen3-Coder-Plus, Doubao-Seed-2.1-Pro, Kimi-K2.6 and MiniMax-M2.7), FULL-REWRITE (the model sees the original and writes its own implementation), COMPLETION (a human prefix is completed), REFACTOR (in-place refactoring, producing many very short AI segments), and FIM (interior spans refilled). The cells differ in how much human text survives in the output, which we find to be the dominant difficulty factor.

## 4.3 BASELINES

Every supervised baseline shares our training split, the same development split for aggregation and threshold selection, and, where applicable, the same scoring backbone. Group A (zero-shot) comprises six likelihood-based statistics: log-rank (Gehrmann et al., 2019), LRR (Su et al., 2023), Fast-DetectGPT (Bao et al., 2024), Binoculars (Hans et al., 2024), DetectCodeGPT (Shi et al., 2025) and the AIGCode Detector (Xu and Sheng, 2024). Group B (supervised) comprises a frozen code encoder (CodeT5+ 220m) with an MLP head, fully fine-tuned CodeBERT (Feng et al., 2020) and UniXcoder (Guo et al., 2022), ImBD (Chen et al., 2025), DroidDetect (Orel et al., 2025), and — the critical control — the same backbone with a LoRA classification head, matched in backbone, data and optimisation schedule, so that the only difference from our method is “classification head versus likelihood ratio”. Group C (ours) is the token-level likelihood ratio, the block head at $K \in \{ 8 , 1 6 \}$ the line head, and their combinations. Scoring and aggregation details are in Appendix A.9.

## 4.4 METRICS

The positive class is AI-involved, so a mixed file is positive whatever its ρ (Section 2). We report AUROC, TPR@1%FPR and macro F1 over the positive and negative files of each comparison, scored on the file score f. An AUROC below 0.500 means the score ranks machine files as more human-like than human files. TPR@1%FPR reads its threshold off the negatives of the same comparison; on the internal test set that is the HUMAN cell of the test set itself, so the operating point is exact rather than transported from development. Macro F1 averages the per-class F1 of the AI class and of the human class, the latter scored on the inverted prediction, which penalizes a detector that calls everything AI-involved; it needs a threshold and the available calibration data differ by corpus, so each table states its own. Accuracy appears only in Appendix A.2: the fraction of mixed files differs between development and test, so a transported threshold is systematically mismatched, which is why the three metrics above are either threshold-free or read at a fixed FPR. Every table in the paper follows the same conventions for metrics, negative pool, chance levels and bolding, and states only its departures from them; table conventions, chance levels, per-cell counts and per-row exceptions are in Appendix A.9.

## 4.5 EXTERNAL BENCHMARKS AND TRANSFER PROTOCOLS

We evaluate on three external resources, none of which shares our generation protocol: AICD-Bench (Orel et al., 2026), used as its binary task T1 and its four-class task T3; DroidCollection (Orel et al., 2025), a multi-generator, multi-task corpus with four authorship classes; and Hybrid-CodeAuthorship (HCA) (Patterson et al., 2026), the only one of the three with per-line ground truth. For the multi-class resources every machine-involved class is mapped to y = 1. Two protocols are reported: P1 transfer with no adaptation; and P2 adaptation on the benchmark’s own training split, which is the protocol under which published numbers were obtained. HCA has no training split, so only P1 is defined there, and it is additionally scored at its native line and block granularity. Group A and the Group B baselines are run on the external benchmarks as well. Composition, file counts, per-slice results and the row set of each table are in Appendix A.10.

Group B changes the picture completely: every supervised baseline reaches 53.1–82.9 on the fromscratch cells, against at most 35.9 for any zero-shot statistic, so what makes specification-based rewriting detectable is supervision on this distribution, not a better likelihood statistic. The informative comparison is the same-backbone LoRA classification head, which shares the backbone, the training files, the tokenizer and the optimisation schedule with our adapters and, at scoring time, the same 4096-token window with 512 tokens of carried context as our own scorer (its file score is the mean over window logits), so its residual gap to the token ratio (60.4 against 70.7 average macro F1) is attributable to the likelihood-ratio formulation rather than to the 1.5B backbone. The gap has two parts. On the from-scratch cells (9.8–17.8 points) it is a tail effect: at the same 1% FPR the token ratio recovers more positives. On COMPL. and FIM it is structural: the classifier stays 3.6 and 1.5 points above the all-negative floor, against 11.4 and 5.5 for the token ratio. A windowed head compresses each window into one decision and averages the windows, so a short inserted span is averaged away, whereas a token-level score keeps it addressable.

Difficulty tracks how much human text survives in the output: REWRITE (87.4) is as easy as the specification-based cells (89.1, 89.4), while COMPL. and FIM, where a human prefix or envelope is left in place, are the two hardest (50.0 and 45.3). The block head’s gain is concentrated exactly there (+10.8 on COMPL. and +5.1 on FIM at $K = 8 ) ;$ ; on the from-scratch cells it costs 2.8 on BASE and 4.1 on REWRITE while gaining 1.3 on UNSEEN, which is the trade-off a localizing read-out makes and the reason we report both. The line head pushes it further (+7.1 on COMPL., +1.8 on FIM, −6.5 to −15.0 on the from-scratch cells) and ends 5.0 points below the token ratio on average: it detects files with an interior AI segment rather than files as a whole.

## 5.2 LOCALIZATION VALUE AND BLOCK SIZE

The cell-level averages of Table 1 conflate how much of a file is AI with how its AI part is laid out, and only the latter bounds what localization can add. Stratifying the three mixed cells by the AI ratio ρ (Table 10, Appendix A.4) shows the bound directly: below $\rho = 0 . 2$ the token ratio and both block heads lie within 0.8 macro F1 of each other (50.4–51.2), while at $\rho \ge 0 . 8$ the K=8 head is 11.9 points above the token ratio (78.4 against 66.5). A supervised unit-level head buys little when the machine-written part of the file is small.

The block size follows the same logic: what matters is whether a block boundary can fall inside an AI segment. When the median segment is close to $K ,$ reducing K improves every bucket; when it is far below any usable K, most blocks are mixed and the larger K wins because each block carries more tokens and less feature noise. The three mixed cells of Table 22 instantiate the three regimes: on FIM (median segment near $K = 8 )$ and COMPL. (one segment far longer than either block) the smaller block wins (50.4 vs. 48.6 and 60.8 vs. 58.5 macro F1), as its interior blocks are pure and the finer grid places the boundary more precisely; on REFAC. (median two lines, below any usable K) the order reverses (62.9 vs. 63.8): no block isolates a segment, so tokens per block outweigh boundary precision. The line head is weaker still (54.8 file-level macro F1, line-level F1 48.0, Table 8): on REFAC. the signal comes from pooling, not localization. ## 5.3 ABLATIONS

The ablations answer five questions: whether the ratio form is doing the work, which token categories carry it, whether any single feature family is load-bearing, how much of the performance depends on the amount of adapter training data, and how much of it depends on the backbone being Qwen2.5-Coder-1.5B. The components sit at two levels, so the panels are read against two refer ences: the token-level panels against $s _ { \mathrm { a i - h u m } }$ with the file-mean aggregation, the block-level panel against the $K = 1 6$ head with logit-mean aggregation. Each row removes or replaces exactly one component.

The token-level panel is the sharpest of the three. Neither half of the decomposition is sufficient: the AI-side deviation alone reaches 0.773 and the human-side deviation alone 0.506, i.e. chance, against 0.838 for the ratio. The asymmetry is the point: a term that cannot rank files at all is worth 0.065 AUROC and 28.2 TPR once subtracted, because what it removes is how predictable the text is: a normalizer, not a detector. Replacing the ratio by the AI-side adapter’s likelihood (0.522) is no better, which rules out reading our score as "the AI-tuned model finds this file predictable".

In the block-level panel no feature family is individually load-bearing: the only two whose removal is a statistically detectable cost (−0.008 for raw, −0.011 for z-scores) are about an order of magnitude cheaper than either half of the ratio, the positional family is within noise on both AUROC columns (−0.001 and −0.002), and the language family is negative — removing it improves both AUROC columns slightly but significantly (+0.003 and +0.005) and leaves the tail unchanged within noise (48.4 → 47.9). The positional result also holds where a shortcut would have to appear, on COMPL., whose AI segment is always at the tail: per-cell ∆ (Table 11) costs at most 0.005 AUROC in any single cell, so the head does not take the positional shortcut.

The third reading concerns the operating point rather than any component. Rows that are nearly free in threshold-free terms are expensive at 1% FPR: removing comment tokens costs 0.035 AUROC but more than half of the TPR (47.1 → 21.4), and a tenth of the adapter data costs 0.055 AUROC and again about 40% of the TPR. Scoring comments alone retains 0.787 AUROC, more than the code-token-only variant (0.744), which is itself 0.244 above chance, so comments are neither the mechanism nor a negligible part of it. A low-false-alarm deployment therefore depends on comment tokens and the full adapter training set — two components AUROC alone calls unimportant.

Swapping Qwen2.5-Coder-1.5B for deepseek-coder-1.3B (Guo et al., 2024) costs 0.012 AUROC and 3.9 TPR — a fifth of the data-quantity row, reversing no cell — although deepseek is the stronger language model, so predictive quality and ratio quality are distinct (Appendix A.5).

## 5.4 IS THE SIGNAL JUST FORMATTING?

Static formatting statistics separate human and machine code to a degree (Nirob et al., 2026), so we bound that explanation from both sides (Table 16, Appendix A.6): a whitespace-only logistic probe trained on the same corpus as the supervised baselines reaches 0.60 average AUROC, the static ceiling, while normalizing all formatting away — provably leaving the non-whitespace character sequence identical — costs the detector 3.5 AUROC points and still leaves the pure cells 25–30 points above their per-cell ceilings. The separation between methods in Table 1 is therefore not layout.

## 5.5 ROBUSTNESS ON REAL HUMAN CODE

A detector is only deployable if its false-positive rate on genuinely human-written code is low, measured on code that predates widespread model assistance rather than on the human side of a synthetic pair. Across 19,445 files from repositories created before 2022, all of them negatives, at thresholds fixed on the development split and not re-tuned, all four read-outs stay between 0.55 and 0.81% against a nominal 1% (Table 18, Appendix A.7), so transporting the operating point from paired synthetic data to real repositories costs essentially nothing. Block- and line-level false-alarm rates on the same corpus are an order of magnitude higher (9.90% and 8.89% for blocks at K = 8 and K = 16, 17.33% for lines; Table 19): the file-level aggregation is what suppresses them, so any deployment that surfaces block- or line-level highlights has to be calibrated separately.

## 6 LIMITATIONS

Our mixed files use few writer models and prompts, and the specification-based construction strips machine-side dead code and license headers, so the numbers are an upper bound, not a deployment estimate. Training sees only long AI segments (median 20 lines), so the scattered regime is measured but never trained on, and the positional family, bounded at −0.001 AUROC here, is not ruled out elsewhere. Byte-identical low-entropy pairs put the same text on both sides as known label noise.

## 7 CONCLUSION

Detecting AI-involved code is a different problem from detecting AI-written code, and the difference is not a matter of degree. Where a generated span sits inside surviving human code, the supervised file-level control that reaches 71.6–79.3 macro F1 on whole machine-written files stays 3.6 and 1.5 points above the all-negative floor, against 11.4 and 5.5 for the token-level likelihood ratio (Table 1): a windowed head averages a short inserted span away, while the ratio between an AI-side and a human-side adapter keeps it addressable and the line and block heads read it where it sits. The mechanisms are therefore complementary rather than competing.

What bounds a localizing read-out is the size of the machine-written part relative to the prediction unit, not the choice of unit: below $\rho = 0 . 2$ the token ratio and both block heads lie within 0.8 macro F1 of each other, and once the median AI segment falls below any usable block — two lines on REFAC. — the ordering of K reverses and the line head drops to 54.8 file-level macro F1 at 48.0 line-level F1, so what remains is pooling rather than attribution. The transfer–adaptation gap carries the same message one level up: most of what separates the classes on AICD-Bench and DroidCollection is specific to how each corpus was generated rather than a property of machinewritten code that survives a change of protocol.

## ETHICS STATEMENT

Detectors of this kind are deployed in assessment and code-provenance settings where a false positive is costly, which is why every headline number in this paper is reported at a low-false-positive operating point and why we measure the false-positive rate on genuinely human code from repositories that predate widespread model assistance rather than on the human side of a synthetic pair. Two consequences of our measurements bear directly on responsible use. First, the false-alarm rate is language-dependent, and the worst per-language rate we observe is an order of magnitude above the aggregate, so a single global threshold disadvantages authors writing in the less-represented languages. Second, block- and line-level highlights carry much higher false-alarm rates than the file-level verdict, so surfacing them to a human reviewer without separate calibration would present unreliable evidence as if it were localized proof. We release no model that scores individual authors, and the training corpus is built from public repositories under their original licenses.

## A.1 EXTENDED RELATED WORK

This section is the related-work discussion deferred from the main text.

Zero-shot likelihood detectors. Zero-shot detectors threshold a likelihood statistic computed under a reference model: perturbation curvature, estimated by mask-filling (Mitchell et al., 2023) or in analytic conditional-probability form (Bao et al., 2024); log-rank (Gehrmann et al., 2019) and its ratios LRR and NPR (Su et al., 2023); and cross-perplexity between a performer and an observer model, which cancels much of the prompt-difficulty confound (Hans et al., 2024). They need no labels and transfer across generators, and they all rest on the premise that machine text is more predictable than human text under a reference model.

Supervised detectors for machine-generated code. DetectCodeGPT is the code-side perturbation detector, inserting newlines and whitespace instead of filling masked natural-language spans, on the observation that machine code is more regular in exactly those positions (Shi et al., 2025). Most supervised code detectors instead train a discriminator on labelled source: CodeBERT- and CodeGPT-based classifiers (Nguyen et al., 2024; Xu et al., 2024), detectors built on surface-form, whitespace or embedding features (Nirob et al., 2026), and function-level detectors for Python (Idialu et al., 2024) and C programs (Bukhari et al., 2023); all of them assume a labelled pool in the language and style of the code under test. ImBD aligns a proxy model to machine stylistic preference by direct preference optimization and then reads a curvature statistic under the aligned model (Chen et al., 2025), the strongest recent supervised-scoring competitor for machine-revised text. Our own supervised controls are described in Section 4.3.

Contrasting two models. A difference of two models’ log-probabilities over a shared backbone is the score form used in decoding-time control — contrastive decoding (Li et al., 2023), DExperts (Liu et al., 2021) and proxy tuning (Liu et al., 2024) — where the two sides are experts steering generation rather than detectors. What we take from that line is the form of the score; what we add is its role as a per-token detection statistic and the sequence heads that read it.

Spans and boundaries in text. Below the document level, the nearest formulations come from machine-generated text detection. SeqXGPT labels machine-written sentences with a token-level classifier (Wang et al., 2023b); SemEval-2024 Task 8 Subtask C asks where the boundary between human and machine spans falls inside a mixed document (Wang et al., 2024a); M4GT-Bench organizes datasets and domains around the same mixed-text setting (Wang et al., 2024b), and RoFT studies where human readers place such boundaries (Dugan et al., 2020). The task is the same here and the structural assumptions are not. Mixed text is generated forward from one prompt, so authorship changes at a point in the sequence and the natural procedures are change-point detection or token tagging. A mixed file is assembled by local edits against a surrounding context, with fillin-the-middle insertions and whole-block rewrites, so AI involvement is block-aligned rather than a single cut. That difference is what our block and line heads encode, and it is why we report attribution at those two granularities instead of a boundary position.

Mixed and fine-grained authorship. Most resources for code authorship operate at the file level: DroidCollection is a multi-generator, multi-domain corpus annotated over four authorship classes, which also ships the fine-tuned encoder detector DroidDetect (Orel et al., 2025), and AICD-Bench stays at the file level and targets out-of-distribution robustness through its own tracks and splits (Orel et al., 2026). HybridCodeAuthorship is the exception: it provides per-line labels for human– AI co-written files with no training split (Patterson et al., 2026), with a median AI segment of two lines.

## A.3 BLOCK-LEVEL METRICS

Block-level AUROC and F1 for each K. All block labels follow Section 2: a block is positive if it contains at least one AI line. On the internal test set this makes 72.0% of blocks positive at $K = 8$ and 74.6% at $K = 1 6$ , and the block head reaches 0.874 AUROC at K = 8 and 0.882 at K = 16 over all blocks, against 0.906 and 0.930 when the metric is restricted to blocks that are pure in content. At the development-frozen threshold its F1 is 82.8 (K = 8) and 80.4 (K = 16), which is below the all-positive floors of 83.7 and 85.5: at a positive rate above 0.7, F1 rewards the degenerate classifier, and AUROC is the comparable reading at this granularity.

Table 7 resolves both K by cell, and it separates two things the pooled numbers above conflate. Within a cell the smaller block is at least as good on all three mixed cells (0.912, 0.648 and 0.650 at K = 8 against 0.897, 0.646 and 0.594 at K = 16), which is the ordering the lower panel of Table 9 also shows; pooled over all blocks the ordering reverses (0.874 against 0.882), because pooling mixes blocks from different cells and the easy separation between the all-positive blocks of the pure cells and the all-negative blocks of the HUMAN cell dominates the ranking. Block size therefore has to be chosen inside a cell, not on the pooled number.

The line head is reported per cell in Table 8, since its line-level behaviour is what bounds a localizefirst pipeline. Line-level AUROC is defined only on the three mixed cells: in the pure cells every line is AI and in the HUMAN cell none is. The pure rows therefore carry a recall but no ranking metric, and the HUMAN row carries neither — with no positive line its recall and F1 are undefined as well, and it appears only to fix the negative pool.

The line-level signal is regime-dependent rather than uniformly weak: 0.927 on COMPL., where the AI part is one long tail segment, against 0.599 on REFAC., whose median segment is two lines, and 0.695 on FIM. On REFAC. the transported line-level F1 is 48.0; on COMPL. it reaches 85.2.

The ten read-outs are implemented as follows. Over the per-block probabilities $\hat { z } _ { b }$ of a file’s block set B: logit mean averages $\sigma ^ { - 1 } ( \hat { z } _ { b } )$ after clipping the probabilities away from 0 and 1 (Equation 2); mean averages $\hat { z } _ { b }$ in probability space instead; top-25% and $t o p \mathbf { - } 1 0 \%$ mean sort the blocks by $\hat { z } _ { b }$ and average the highest ⌈0.25|B|⌉ and ⌈0.10|B|⌉ of them, at least one block in either case; max takes the single highest $\hat { z } _ { b } ,$ , which carries a length bias the two top-share means do not, since a file with more blocks has a systematically higher extreme; and best adjacent pair is ma $\mathrm { x } _ { b }$ min $\left( \hat { z } _ { b } , \hat { z } _ { b + 1 } \right)$ , a “two blocks in a row are high” statistic that encodes the prior that an AI segment covers more than one block and is less sensitive to a single noisy block than the max. Over the per-token ratio $s _ { t } \colon$ file mean is Equation 2; sliding-window max takes the largest within-window mean of $s _ { t }$ over 128-token windows at stride 32, falling back to the file mean for files shorter than one window; change-point tail places a single cut with a CUSUM statistic on $s _ { t }$ and averages the tokens after it, keeping the file mean when fewer than 8 tokens remain; and best segment splits the file by recursive binary segmentation — at most 8 cuts, each segment at least 16 tokens, and a split accepted only if its CUSUM statistic clears a gate fixed on the development split — and takes the largest per-segment mean.

At the block level the entire choice is worth 0.007 AUROC, and the development-selected logit mean is not the optimum on the mixed cells, where plain mean, top-25% and K=8 are 0.004–0.013 higher; we keep the development choice rather than reporting the test-optimal one. At the token level the choice matters at the operating point rather than in AUROC: the change-point tail mean keeps 0.820 AUROC but loses more than half of the TPR at 1% FPR (47.1 → 22.4), whereas the bestsegment variant is indistinguishable from the plain mean. Neither of the two localization-flavoured aggregations of the token score buys anything over averaging it, which is the reason the block head, and not a segmentation of the token sequence, is our attribution read-out.

Line-head read-out and its positional information. The line head consumes the same token profile as the block head and differs only in supervision granularity, so its read-out is ablated separately (Table 13). The learned aggregator over line states is a small Transformer, which is equivariant to a permutation of the lines: the position of a line inside the file can only reach it through the sinusoidal encoding, and removing that encoding is therefore the positional ablation on this path.

Averaging the line logits is the best read-out of the line head: the max is 0.004 below it and the learned aggregator 0.009 below, the latter losing a third of the TPR at 1% FPR. Removing the positional encoding does not hurt the aggregator — it closes the gap to the line mean (−0.001, interval containing zero) and gains 0.007 on the mixed cells — so on this path too the model is not using where in the file a segment sits. How the block supervision is constructed. Section 3.4 makes two choices that can be ablated by retraining the head on a different corpus: mixing two synthesis forms, and keeping the paired human original of every mixed file as a negative. Table 14 does that, and its own training diagnostics are the reason we read it as a data-volume result rather than as a construction result.

The diagnostics have to be read before the ∆ column. The reference stops improving on development after 4 epochs at a block-level AUROC of 0.914; every reduced-corpus run peaks after a single epoch at 0.62–0.82 and then descends monotonically while its training loss falls to 0.003, and pinning all runs to 4 epochs reproduces the same development AUROC to three decimals. The head therefore memorizes a reduced corpus, which means these differences conflate the construction with an optimisation failure, and we report them as a sensitivity to corpus volume rather than as the effect of the construction.

Within that limit one comparison is still clean. Continuation only (11,111 pure blocks) is above the volume-matched subsample that keeps both forms (10,807 blocks): 0.730 against 0.683. We therefore have no evidence that mixing continuation with fill-in-the-middle supervision is what the block head needs; what the numbers support is the weaker statement that it needs volume (17,767 blocks → 0.853, roughly 11,000 blocks → 0.68–0.73 regardless of form). Removing the paired human originals costs 0.077 AUROC and half of the TPR, in the direction Section 3.4 predicts, but that corpus is also the smallest of the six, so that row does not separate the paired negative from the volume either. One further choice is not load-bearing: weighting the loss so that every file contributes equally, rather than every block, changes the average AUROC by +0.001 and the TPR by +0.0 points.

## A.6 FORMATTING CONTROLS

Table 16 is the evidence behind Section 5.4, and it bounds the formatting explanation from two sides. The left panel is a static ceiling: a logistic probe trained on the same corpus as the supervised baselines, restricted to whitespace features, reaches only 0.64–0.67 AUROC on the pure cells, 0.54 on COMPL., and chance level on FIM; with file length alone the probe is near chance on every cell.

The right panel intervenes on the input instead: we erase formatting from the files and re-score them with the unchanged detector. Two levels of normalization are applied, in the following order.

Soft unifies line endings (CRLF and lone CR become LF), then strips trailing spaces and tabs from every line, then collapses each run of blank lines to a single blank line and drops the file’s leading and trailing blank lines. Indentation and intra-line whitespace are left untouched, so the code remains syntactically valid in any language.

Hard applies Soft first and then, line by line, removes all leading spaces and tabs, collapses every remaining run of spaces and tabs inside the line to a single space, and deletes blank lines entirely. This destroys every whitespace statistic — indentation width, blank-line structure and alignment alike (Python files lose their block structure; the scorer reads the file as text and does not require compilable code).

Every operation at both levels only deletes or merges space, tab and newline characters and never touches a non-whitespace one, which is why both levels provably leave the non-whitespace character sequence identical to the original file. Erasing formatting entirely leaves the detector far above the whitespace ceiling of the left panel and above every zero-shot method, at the cost read off in Section 5.4; the one cell that moves the other way is FIM, which improves by 1.7 points, indicating that indentation was acting as noise there. The detector reads the code, not the layout.

## A.8 IMPLEMENTATION DETAILS

The scoring backbone is Qwen/Qwen2.5-Coder-1.5B, kept frozen throughout. Each adapter is a rank-16 LoRA module with $\alpha = 3 2$ and 18.5M trainable parameters, targeting q\_proj, k\_proj, $\mathtt { v \_ p r o j , o \_ p r o j }$ , gate\_proj, up\_proj and down\_proj, and trained with AdamW at learning rate $1 0 ^ { - 4 }$ for one epoch on its own side of the pure-file split with a plain causal language modeling objective, truncating each file to 2048 tokens (the 90th percentile of the length distribution; 5–7% of training files are cut). Training and scoring run in fp16: the available accelerators are Volta-class and have no bf16 hardware, so bf16 would fall back to an emulation path. Batching is by token budget over length-sorted buckets, with gradient checkpointing enabled and no sequence packing.

Scoring is windowed rather than truncated. The per-token profile pass uses a 4096-token window with 512 tokens of carried context, which keeps files of any length scoreable. Training truncates at 2048 tokens while scoring reads 4096-token windows, so the positions and relative distances beyond 2048 are extrapolated at scoring time: the backbone’s rotary embeddings are defined up to 32,768 positions, so this is a distribution shift rather than an out-of-range error, and every scored token still carries at least 512 tokens of real left context. The logit computation is sliced so that the vocabulary-sized intermediate never materializes for the whole window at once. The base-mode pass additionally emits entropy and rank, and a second pass over a short context window supplies the short-context contrast features. Token scores are persisted at float32, so changing K does not require re-scoring.

The block head is a bidirectional GRU over the 88-dimensional block feature sequence, trained on GPU; mixed blocks are masked out of the loss. Its aggregator and K are chosen on the development split. Both heads use 2 layers of hidden size 64, dropout 0.1, Adam (Kingma & Ba, 2015) at 10<sup>−3</sup>, at most 60 epochs with early stopping on the development split after 8 epochs without improvement, and seed 20260907; the block head batches 32 files at a time while the line head batches by a paddedtoken budget of 131,072, since single files of several thousand lines make a fixed file count overflow memory.

Head input features. Table 21 lists both heads’ inputs. The block head’s 88 columns form five families, named by the prefix that the drop-family rows of Table 2 remove. log-rank is log(1+rank): the raw rank is long-tailed to 65,535, and on a linear scale a few large values dominate the block mean. Every signal statistic is given twice, once as a raw value and once as a within-file z-score whose mean and standard deviation are computed after 1%/99% winsorization, and the two are not redundant. With raw values only, how predictable a file is overall becomes a confound that masks between-block differences; with z-scores only, every block of a pure-AI file sits near its own file mean and is hard to separate from a block of a pure human file, while the file score is an aggregate of block logits. Removing either family is detectable but small on the test cells (−0.008 and −0.011 AUROC, Table 2), so this is a design argument, not a large effect. Blocks containing no token at all are dropped rather than zero-filled, which would enter the head as neutral evidence; for an out-ofrange or empty neighbour in the ctx family the neighbour value falls back to the block itself, the difference is set to zero, and a miss flag is raised. The line head takes the same token profile but only 16 columns, and in particular no positional, language or size feature.
