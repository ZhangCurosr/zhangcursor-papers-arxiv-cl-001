# Persistent Memory in Multi-Agent LLM Inference: What It Costs, What It Buys, and When You Can Tell

Hochan Son<sup>1∗</sup> Kyungdoe Han<sup>2</sup> Jaehan Koh<sup>3</sup> Xiaowu Dai<sup>1</sup> Wenlu Xu<sup>1</sup> Guang Cheng<sup>1†</sup>

<sup>1</sup>University of California, Los Angeles <sup>2</sup>University of Wisconsin <sup>3</sup>HCLTech America

## Abstract

Decomposing long-context inference across cooperating agents bounds the active KV cache per call rather than total evidence, which matters when KV-cache memory binds. Many such systems add a persistent tier storing and recalling reasoning traces, usually validated by an ablation reporting an accuracy gain. We measure both on one three-tier agent architecture. Decomposition delivers: peak KV working set of 14.3 MiB per query against 35.5 and 35.3 MiB for single-pass and retrieval-augmented baselines. The persistent tier does not: across eight controlled dataset pairs at n=100 per arm it costs +0.368 MiB [+0.167, +0.590] of peak cache and produces no detectable accuracy change (+0.015, 95% CI [−0.011, +0.046]). We argue the null is structural: single-question benchmarks supply each item with its own evidence and score it independently, and correctness requires resetting stored traces between conditions, so recall has nothing informative to retrieve. Reaching it took four measurement corrections—three inflating the apparent benefit, the fourth making an effect that size look resolvable—none visible in the results table. We give the conditions an agent-memory ablation must satisfy and detection procedures that need no knowledge of the specific defect.

## 1 Bounding the working set, and the tier that is hard to test

The KV cache is the memory bottleneck of long-context inference: it grows with context, is provisioned against its peak, not its average, and routinely exceeds an edge accelerator’s VRAM, which is why cache management is a systems problem in its own right [Kwon et al., 2023]. One response is architectural: if a task is decomposed across agents, each handling part of the evidence and passing distilled state onward [Zhang et al., 2024], no single call holds the whole context and the active working set stays bounded as total evidence grows.

Systems in this family commonly add a further tier: a persistent store keeping each query’s reasoning trace and retrieving relevant ones later. The argument is intuitive—an agent that remembers should need less context—and is usually supported by an ablation that disables the tier and reports an accuracy drop.

We measure both on one such system. The first holds; the second does not—and we argue the way these systems are evaluated makes it very difficult either for it to hold or for a reported gain to mean what it appears to.

What is new here. Retrieval augmentation and agent decomposition are routinely treated as interchangeable answers to long context. For memory they are not: RAG changes which evidence enters a call; decomposition changes how many calls it is spread across, and only the second bounds the peak KV. Our retrieval-matched RAG baseline still concatenates its passages into one generation call and measures a peak indistinguishable from closed-book single-pass (Table 1): filtering evidence better does not shrink the largest call. To our knowledge no prior work reports an agent architecture’s peak KV as a measured, ablated systems quantity (§6); that decomposition alone bounds it, independent of any persistent-recall tier, is our first contribution and §3–4’s null the second. We do not claim persistent recall improves accuracy: that is untested, not disproven.

The architecture. Figure 1 shows the system. L1 is the ephemeral per-call KV cache. L2 is a key– value store of typed Communication Units, so an agent receives distilled predecessor output rather than raw context. L3 is a vector store whose two roles—semantic evidence filtering before anything enters a cache, and $( q , k , v )$ trace persistence for cross-query recall—are separable in code; only the second is the persistent-memory claim. We call the full system COA-PKV—chain of agents over a persistent key–value tier—and the arm with trace recall and writes disabled COA-NOKV; they differ in exactly those two operations, L1, L2 and evidence filtering untouched in both.

## 3 The persistent tier costs memory and buys nothing measurable

## 4 Why the null is structural

The result is not that our persistent memory is poor, but that the regime we—and many systems papers—evaluate in cannot exercise it. That multi-session interaction is required to test memory is established: LoCoMo [Maharana et al., 2024] and LongMemEval [Wu et al., 2025] exist because single-session QA does not probe it. We quantify that observation’s consequence: what a correctly isolated ablation returns when a system is evaluated on independent-item benchmarks anyway, and what makes it return something else. Two properties compose to force the null.

Items are independent and self-supplied. Benchmarks of this kind present each question with its own gold or retrieved evidence and score it in isolation. Nothing a system learns on question i is intended to be useful for question j.

Correctness forces the reset. Recall retrieves by question embedding, so at a fixed seed a re-run retrieves its own prior conclusions (§5, C2). Preventing that requires clearing stored traces between conditions. But then within-condition recall can only reach traces from other, unrelated items in the same run.

Measured, not assumed. Reproducing the retriever’s predicate exactly—same embedding model, same 0.6 threshold, only traces written earlier in the same run—recall was reachable for 24% of questions as sent (20% once each cell’s shared instruction boilerplate is stripped; Appendix A.5); for the rest it provably returned nothing, so §3’s figure is intention-to-treat. Restricted to questions where recall could fire the effect is −0.012 [−0.073, +0.046] (n=138)—a wider interval than the aggregate—while questions where it provably could not act as a built-in control and give +0.009 [−0.007, +0.026], consistent with zero as required. The aggregate is thus correctly measured but uninformative about efficacy, and the subgroup that tests efficacy is underpowered—a distinction applying to any such ablation. The transferable point is the contrapositive, uncomfortable because the practice is common: a non-zero memory effect reported on an independent-item benchmark is more likely an artifact than a finding. Systems papers routinely support a memory tier with exactly such an ablation; we did, with four artifacts (§5) present at once—three inflating the effect, the fourth making it look resolvable. Testing the claim requires a regime where items genuinely share state—multi-session dialogue, a corpus queried repeatedly, an agent revisiting entities—and where the reset that prevents contamination does not destroy the signal.

## 5 Conditions an agent-memory ablation must satisfy

We reached §3’s measurement only after four corrections, stated as conditions rather than bugs: each was satisfied in appearance and violated in fact. C1–C3 each independently produced an apparent memory benefit; C4 made effects that size look resolvable.

C1 — The component executed. Our persistent tier wrote traces nothing ever read: both arms of every prior memory ablation ran with no memory. Three further components were similarly inert— a client-side ablation flag for a server-side agent, a reranker whose 404s became “keep existing order”, a cost accumulator off the benchmark path that zeroed 38 published cells. Each is correct code implementing a degradation that was total, permanent and indistinguishable from success. Detection: emit a counter for every component whose presence is a claim and assert it non-zero in the run summary—not a log line, a counter the summary refuses to omit.

C2 — Runs were independent. With traces keyed by question embedding, a fixed-seed re-run retrieves its own previous answers; we measured 100/100 of a run’s questions already carrying a stored trace, from 48,915 traces over 2,856 questions. The signature is detectable retrospectively without instrumentation: within groups sharing code version, n and seed, score rises monotonically with run order in 6 of 6 groups on our most entity-dense dataset (p ≈ 0.0006), with no such pattern where cross-item entity reuse is lower. Correcting it moved one dataset 0.2949 → 0.2282— downward, the direction sanity-checking never catches. Detection: query the store with the evaluation questions before running; any hit above threshold is contamination.

C3 — Only the named axis varied. Our original ablation switch disabled memory and moved execution from a service to in-process and changed the evidence source and the dependency set. The cost is concrete: an uncorrected MMLU-Pro pair read +0.370, a 37-point apparent memory win produced by an option-letter extraction step fixed in one arm and not the other; with both arms on the same parser the cell reads +0.010. A subtler instance is time: execution was systematically order-confounded—the memory-enabled arm ran first in all eight pairs—while our serving stack slowed ≈3.5× across a multi-day campaign. Within a pair the arms ran at the same speed, but memory-off failed more: 20 orchestrator give-ups to 1, client timeouts level at 3 (Appendix A.2); with order and arm confounded, the record cannot say why. Detection: diff the arms’ serialised requests—they must differ in exactly one field—then counterbalance order, since a diff cannot see time.

C4 — The effect exceeds the measurement floor. Pooled within-configuration standard deviation—across replicate groups sharing code version, n and seed—is 0.046 and 0.052 on our two multi-hop datasets, giving 95% bands of ±0.09–0.10; every architecture-vs-baseline delta we had been prepared to quote was smaller. Detection: estimate the band from replicates, not a within-run bootstrap, which measures sampling error only and understated our uncertainty twofold [Bouthillier et al., 2021]. Under C2’s reset protocol the band is far tighter (Appendix A.4).

Why trust a paper reporting four confounds not to have a fifth? The corrections moved cells both ways—two up, one down, two reverted—the signature of measurement, not tuning (Appendix A.4).

## 6 Related work

Agent decomposition [Zhang et al., 2024] and retrieval augmentation [Lewis et al., 2020] are established responses to context limits; we combine both with a persistent tier, and both motivate decomposition by accuracy, not memory. KV cache management [Kwon et al., 2023] optimises the cache for a given workload rather than asking whether an architectural choice changes its peak demand— complementary to our question. The agent-memory literature (§4) establishes that multi-session regimes are required, not what happens outside one—our subject. Our bands follow Bouthillier et al. [2021]; C2’s contamination channel has no counterpart in single-model benchmarking.

## 7 Limitations and Future Work

Single system, single team; the conditions are general in aim, not frequency, and reconstructed rather than derived. Bands rest on 2–4 replicates and §2’s FLAT arm is single-run. Future work: replicate every §2 arm to RAG’s three runs per cell, a context-length scaling study, and §4’s regime—where agent memory’s accuracy becomes testable, not merely untested.

## A.1 Reproducibility and implementation

The controller runs six nodes—Decomposer, Retriever, Reasoner, Critic, Synthesiser and a separate answer critic—over the three memory tiers named throughout this paper: L1, a flat, ephemeral per-call context window (not to be confused with the FLAT baseline arm in §2, which is an entire inference pipeline rather than a memory tier); L2, a Redis-backed key-value store carrying typed Communication Units between agents; and L3, a Qdrant vector database performing both evidence filtering and, when enabled, persistent trace recall and write.

Inference is served from two heterogeneous edge accelerators rather than a single data-center GPU: an NVIDIA Jetson Orin Nano Super (8 GB) running llama.cpp with a Qwen3.5-2B parameter model, and an NVIDIA DGX Spark running vLLM with Qwen3.5-35B-A3B-FP8 (35B total parameters, ≈3B active). Its hybrid attention keeps a growing KV cache on only 10 of 40 layers, giving the $2 \times 1 0 \times 2 \times 2 5 6 \times 1 8 ( \mathrm { f p 8 } ) = 1 0 , 2 \bar { 4 } 0 \mathrm { E }$ /token used to convert every KV figure in this paper. Both are on-premises edge devices rather than a cloud API—the deployment regime the peak-KV argument in $\ S 2$ is meant to address. The Reasoner and Synthesiser run on the vLLM node; the Decomposer, Retriever, Critic and answer critic run on the Jetson’s smaller model, whose per-token KV footprint is lower. Our accumulator records the peak call’s size but not which agent issued it, so every call is converted at the vLLM model’s geometry. That can only overstate our own peak—a Jetson call scored at the larger model’s geometry is counted heavier than it was—and the FLAT and RAG baselines’ single generation call runs on the vLLM node in any case. The codebase—agents, controller, memory tiers, and the benchmarking and audit tooling used throughout this paper—will be released as an open-source repository.

Peak KV is not device occupancy. Every peak-KV figure counts the attention cache of one call, on the 10 full-attention layers above. It leaves out the per-sequence state the other 30 (linear-attention) layers carry, which the 10,240 B/token constant does not include; the rounding of cache allocation to fixed-size pages; the model weights; and the serving engine’s limit on concurrent sequences, which can bind before the KV cache does. A lower peak KV is therefore headroom in the KV cache, not a proportional gain in sequences per device.

## Ablation isolation protocol

A cell is admitted only if both arms satisfy all of the following. The checks are mechanical and are applied by a script over the stored run records, not by inspection.

1. The memory-disabled arm was produced by the server-side request field, not by any clientside switch. Provenance is recorded per run; an unreadable record counts as failing, since guessing “clean” is how a confounded run re-enters.

2. Both arms record the same dataset, subset, n, seed, evidence-scoping flag and service endpoint.

3. The reference arm has memory enabled, so the pair has contrast.

4. Stored traces were cleared before each arm, and the evidence pool was not. Clearing evidence would drive retrieval precision toward 1.0 and collapse the axis under study; clearing traces is what prevents the contamination in condition C2.

5. Isolation was verified live in the same window: a probe issues one query with memory enabled and one disabled, and requires the recall path to appear in the first and be absent from the second. A one-directional check is insufficient, because an unconfigured store also produces no recall.

Runs failing any check are reported as gaps rather than numbers. Eight cells pass and are pooled in Table 3; LB-All passes but is reported separately because it overlaps three of them. The remainder are excluded rather than mixed in.

Why LB-All is reported but not pooled. It is the harness’s combined LongBench setting, drawing items from the same three subsets that already appear as LB-HotpotQA, LB-2WikiMultihopQA and LB-MuSiQue. The cluster bootstrap treats cells as independent units, so pooling it would resample the same questions under two labels and understate the interval. The exclusion follows from that overlap alone.

It is nonetheless the sharpest illustration of condition C3 in our data. Its arms differ by 1 (memoryon) versus 17 (memory-off) failed questions—the largest asymmetry we recorded. The 17 are connections refused on the run’s last questions, during an orchestrator outage in the second arm; they never reached the pipeline. Since failed questions score zero, its accuracy delta reads +0.071 under our primary convention and −0.006 with every question either arm failed dropped. Had we pooled it, the across-cell accuracy interval would have shifted to [+0.001, +0.065] and excluded zero: a marginally significant memory benefit produced entirely by a serving outage during one arm. We record this because it is precisely the failure the conditions are meant to catch, and it would have been easy to accept.

Among pooled cells the GPQA delta is the largest and also carries the most extreme failure asymmetry (1 memory-on versus 11 memory-off, all orchestrator give-ups); dropping every question either arm failed reduces it to +0.023, and the across-cell figure from +0.015 to +0.003. This is the convention dependence noted in the main text; we report the failures-score-zero figure as primary because it is the convention under which the arms are scored identically, and disclose the other because the difference is not negligible.

What the record calls a timeout. The per-question flag both conventions read marks every failed question, whatever the cause. Over the eight pooled pairs’ 794 paired questions, memory-on and memory-off fail 7 and 23 times: 3 and 3 client timeouts (900 s), 1 and 20 orchestrator give-ups (HTTP 500, “Pipeline returned no answer after 3 attempts”, with no pipeline step or cause recorded), and 3 and 0 server disconnects. The memory-off give-ups all sit in HotpotQA, GPQA and LB-HotpotQA, run on 20 August: memory-on runs finished 09:08–12:42 UTC, memory-off runs 17:36– 21:24. Within every pair the arms ran at the same speed (median per-question latency ratio, memoryoff over memory-on, on questions both answered: 1.00–1.03), so the campaign’s ≈3.5× slowdown does not explain the gap. With memory-on always first, and on that day also hours earlier, the record cannot say whether the arm, the order or the time of day caused it; only a counterbalanced repeat can.

## A.3 Intervals

Deltas are paired per question rather than computed from run-level means. Question difficulty varies far more than the ablated component does, and pairing removes that variance; matching is on question text rather than row position, since a dropped sample would otherwise silently pair question i against question i+1.

Per-cell intervals are percentile bootstrap over the paired deltas, $B = 1 0 ^ { 4 }$ . The across-cell interval is a two-stage cluster bootstrap: resample cells with replacement, then questions with replacement within each drawn cell. Pooling all questions into one sample would treat several hundred correlated observations as independent and understate the interval, because questions within a cell share a dataset, a prompt format and a difficulty profile. The cell is the independent unit.

What the paired columns cover. The two columns of Table 3 are not computed over the same set, so each carries its own n. Accuracy pairs every question both arms scored—a failed question scores 0 and is included, which is the failures-score-0 convention §3 quotes—so n is 100 except where a question is absent from a run entirely. Peak KV pairs only questions for which both arms recorded a cache figure; a failed question produces no peak, so its KV n is 100 minus roughly each cell’s failure count. The released kv\_layer\_cost\_ci.py prints the resolved run ids and both per-cell n values, so the set behind every column is re-derivable rather than taken on trust.

Peak KV is the largest single call’s (prompt + generated) footprint within a query, not the sum over calls. The sum answers a different question—total tokens processed—and is roughly four times larger; using it would overstate the resource being claimed. Both are recorded per query.

## A.4 Reproducibility bands

Bands are estimated from replicate groups: runs sharing code version, n and seed, so that neither code nor sample composition can contribute to the spread. Pooled within-group standard deviation is 0.046 across six groups on MuSiQue and 0.052 across four groups on 2WikiMultihopQA, giving 95% bands of ±0.09 and ±0.10.

Group sizes are two to four runs, so the bands are themselves imprecise; they are sufficient to establish that deltas below 0.06 are not resolvable, which is the use we make of them, and not to quote to three digits.

These MuSiQue groups serve twice: they estimate the band above and supply condition C2’s runorder test below. If run order moves scores within a group, the within-group spread absorbs that movement, so the band is inflated rather than tight—the conservative direction, given that we use it only to rule deltas unresolvable.

The run-order test in condition C2 compares each group’s scores in chronological order. On MuSiQue all six groups are strictly increasing. With group sizes $( 2 , 3 , 3 , 2 , 3 , \bar { 2 } )$ and orderings assumed uniform, the probability of that pattern arising by chance is $( \mathrm { { 1 / 2 ! } ) ^ { 3 } ( 1 / 3 ! ) ^ { 3 } \approx 5 . 8 \times 1 0 ^ { - 4 } }$ The comparison dataset shows one of four, consistent with chance.

Post-submission measurement. The bands above are the historical spread, from replicate groups that predate the trace-reset protocol of condition C2. Re-measuring the same two datasets under the protocol—four replicates each, fixed seed, traces reset between runs—gives a within-configuration standard deviation of 0.003 (MuSiQue) and 0.007 (2WikiMQA), an order of magnitude tighter, and on a subsequent repair of the serving stack the four replicates of each were identical $( \sigma = 0 )$ . As 95% bands that is ±0.006–0.014 rather than ±0.09, comfortably inside the ≈0.046 bound of §3. The floor quoted in C4 is therefore an upper bound inherited from the contaminated regime, not a property of the measurement: under the protocol, run-to-run drift on these datasets is not the binding uncertainty. We report the historical figure because it is what the deltas in this paper were judged against, and the tighter one because it is what a reader reproducing the work should expect.

## A.5 Recall reachability

Reproduces the retriever’s own predicate rather than proxying it: search\_outputs returns stored traces within cosine 0.6 of the current question under sentence-transformers/all-MiniLM-L6-v2. Because resets clear the store between conditions and items are processed in a fixed order, a question can only reach traces written earlier in its own run; we count those. A count of zero means recall provably returned nothing, which is what makes the unreachable group a control rather than a comparison. This analysis covers the six multi-hop and multiple-choice cells it was originally computed on, plus LB-All; NarrativeQA and Qasper, added to the ablation later, are not re-embedded here. The reachability rate in §4 is over the six cells (136 of 575 answered questions reachable as-sent); its effect split also counts LB-All’s two reachable questions, giving n=138. Neither covers all eight cells in Table 3.

As-sent versus content-only. Multiple-choice datasets wrap every item in identical instruction text—the stored query for MMLU-Pro is 1,499 characters opening with the same preamble for all 100 items—and that boilerplate carries enough embedding mass to clear the threshold on its own. Stripping the prefix and suffix shared by every question in a cell halves the apparent reachability of LB-2WikiMultihopQA (10% → 1%) and LB-MuSiQue (16% → 7%): roughly half their recall was firing on template text. “Reachable” should therefore be read as the retriever would have returned something, not as something useful was available. MMLU-Pro is unchanged at 86% because its items genuinely share subject vocabulary, and it is also the cell where recall fires most and still does not help (−0.012).

Two caveats. The reachability figure is threshold- and embedding-dependent; at a looser threshold more questions become reachable and the subgroup grows. And LB-All’s −0.400 rests on two questions—noise, reported only for completeness. Failed questions are excluded throughout, since they score zero regardless of memory and their cross-arm asymmetry is confounded with order (Appendix A.2).

## A.6 What is not reported here

Three things are measured but deliberately outside this paper’s scope: the full accuracy comparison against the retrieval-matched baseline, the cumulative-traffic and throughput characterisation, and the architecture’s design rationale. The first two are summarised in §2 only to the extent needed to establish that the decomposition delivers a bounded working set, which is the premise of the memory question. A context-length scaling study, which would connect the working-set result to an asymptotic cost model, has not been run and is stated as a limitation rather than claimed.
